# Live Shelf → Luna Hub Lite Cloud Integration

**Date:** 2026-04-19
**Status:** Architecture v3 (pull-per-event, no images)

## 1. Operating model

- **Cloud (Supabase) = source of truth** for products + stock + macros.
- **Pi = sensor + AI layer** that watches physical scales/cameras and posts back events describing what changed in inventory.
- **No images in the cloud** (for now). Reference photos, session frames, videos all stay local on the Pi.
- **Pull-per-event, not sync loops.** When an event arrives, the Pi fetches the user's current catalog + stock from the cloud in one call, runs the classifier, and posts the decision back. No background syncer, no cache staleness. Offline events queue locally and drain when the network returns.
- **Pi is a single cloud device** under the user's account. Scales connected to the Pi (live shelf / catch-all / single-item) are identified by a `scale_id` string on each event, not as separate cloud devices.

```
 ┌──────────────────┐              ┌──────────────────────────┐
 │  ESP scales      │              │      Supabase            │
 │  (LAN only)      │              │                          │
 │                  │              │  chefbyte.products       │
 │       │          │              │  chefbyte.stock          │
 │       ▼          │              │   └─ last_update_source  │
 │  Raspberry Pi    │              │                          │
 │                  │              │  chefbyte.live_shelf_*   │
 │  per event:      │              │  private.apply_shelf_... │
 │  1. GET /catalog │◀────HTTPS────┤                          │
 │  2. classify     │              │  Edge fn: shelf-ingest/  │
 │  3. POST /event  │────HTTPS────▶│    /catalog (read)       │
 │                  │              │    /event   (write)      │
 │  + periodic:     │              │    /heartbeat (status)   │
 │    /heartbeat    │              │                          │
 └──────────────────┘              └──────────────────────────┘
```

## 2. What moves, what stays

### Stays on Pi (unchanged)

- CV classifier, reconciler, in-flight tracker, session lifecycle
- Reference photos, session frames, videos (never uploaded)
- Review queue (still Pi-local; cloud only sees the _count_)
- Barcode intake flow: scanner physically on Pi, captures ref photos to local disk

### New on Pi

- `server/cloud/client.py` — HTTPS client with `x-api-key` auth; fails fast — retries handled by `worker.py`
- `server/cloud/catalog.py` — `fetch_catalog()` called per event
- `server/cloud/outbox.py` — SQLite queue for events when cloud is unreachable
- `server/cloud/worker.py` — drains outbox + heartbeats on a background thread
- Classifier candidate-pool builder swapped: reads from the just-fetched cloud catalog instead of local `products` table
- Reconciler commit hook enqueues one event row to outbox per committed mutation
- Product intake writes to cloud (`POST /intake`) instead of local `products` table

### Cloud new

- Six migrations (see §4 below): tables + columns + plpgsql function + wrapper + idempotency log + hardening
- One edge function: `shelf-ingest/` with 4 endpoints
- `chefbyte.shelf_event_log` table for wire-level idempotency keyed on `(user_id, client_event_id)`
- `chefbyte.apply_shelf_event_admin(...)` — thin pass-through wrapper in the `chefbyte` schema, because PostgREST cannot expose functions in the `private` schema directly
- ChefByte UI: one Settings tab ("Scales") + inventory row tag + "Review (N)" button

## 3. Wire protocol

All endpoints on one edge function `shelf-ingest/`, auth via `x-api-key` → SHA-256 → lookup in `chefbyte.live_shelf_devices`. `verify_jwt = false`.

| Verb   | Path         | Purpose                                                                                                                 |
| ------ | ------------ | ----------------------------------------------------------------------------------------------------------------------- |
| `GET`  | `/catalog`   | Returns `{products, stock, pairings, locations}` in one payload (non-depleted stock only)                               |
| `POST` | `/event`     | Apply a scale event to stock + macros (atomic via plpgsql); 1 event per call; `client_event_id` REQUIRED — absent → 400 |
| `POST` | `/intake`    | Create/upsert a row in `chefbyte.products` (called during Pi barcode intake)                                            |
| `POST` | `/heartbeat` | Update device `last_heartbeat_ts`, `lan_ip`, `pending_review_count`, and per-scale `scale_pairings` rows                |

`analyze-product` is not re-implemented — Pi calls it directly (it already exists and already accepts authenticated calls).

### Idempotency

Every `/event` payload MUST include `client_event_id`: a UUID4 string (≤128 chars) generated by the Pi when the outbox row is created. The cloud uses `(user_id, client_event_id)` uniqueness in `chefbyte.shelf_event_log` to dedup. If the same `client_event_id` is replayed (outbox retry after a partial success / network loss), the server returns the cached result — `{ok: true, applied: false, reason: "duplicate", resolved_lot_id: <original>}` — without mutating stock a second time.

The claim/replay is owned by `private.apply_shelf_event` itself (its first statement is `INSERT INTO shelf_event_log ... ON CONFLICT (user_id, client_event_id) DO NOTHING RETURNING`), so it shares a transaction with the stock mutation and the check/apply race is closed.

## 4. Database changes

Shipped as five migrations (applied in order). Each one isolates a concern so the deployment window can stop mid-way without leaving the schema in a broken state.

| `20260419020000_live_shelf_lan_ip.sql`      | `lan_ip` column on `live_shelf_devices` (for "Review (N)" deep-link to the Pi)                                                                                                                                                                                                                                                                                                                                                 |

| `20260419040000_shelf_ingest_fixes.sql`     | Adds `chefbyte.shelf_event_log` (idempotency), fixes `hub.profile` → `hub.profiles` typo, hardens `apply_shelf_event` `added` branch to skip zero-qty lots and guard negative fallback inserts                                                                                                                                                                                                                                 |

Summarized schema after all five migrations:

```sql
-- Device registry (one row per Pi)
CREATE TABLE chefbyte.live_shelf_devices (
  device_id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id              UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  device_name          TEXT NOT NULL,
  import_key_hash      TEXT NOT NULL UNIQUE,
  is_active            BOOLEAN NOT NULL DEFAULT true,
  last_heartbeat_ts    TIMESTAMPTZ,
  pending_review_count INTEGER NOT NULL DEFAULT 0,
  lan_ip               TEXT,                  -- 020000 (IPv4 or hostname shape)
  created_at           TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Pairing for single-item scales + tracking for all scales under a device
CREATE TABLE chefbyte.scale_pairings (
  pairing_id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id            UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  device_id          UUID NOT NULL REFERENCES chefbyte.live_shelf_devices(device_id) ON DELETE CASCADE,
  scale_id           TEXT NOT NULL,
  kind               TEXT NOT NULL CHECK (kind IN ('live_shelf','live_scale','catch_all')),
  product_id         UUID REFERENCES chefbyte.products(product_id) ON DELETE SET NULL,
  first_seen_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
  last_heartbeat_ts  TIMESTAMPTZ,
  UNIQUE (device_id, scale_id)
);

-- Wire-level idempotency log (040000, hardened in 050000)
CREATE TABLE chefbyte.shelf_event_log (
  event_id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id          UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  device_id        UUID NOT NULL REFERENCES chefbyte.live_shelf_devices(device_id) ON DELETE CASCADE,
  client_event_id  TEXT NOT NULL,
  payload          JSONB NOT NULL,
  applied          BOOLEAN NOT NULL,
  resolved_lot_id  UUID,
  reason           TEXT,
  created_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (user_id, client_event_id),
  CHECK (char_length(client_event_id) <= 128)
);

-- Columns added to chefbyte.products (010000 + 050000)
ALTER TABLE chefbyte.products
  ADD COLUMN net_weight_g     NUMERIC(10,3),   -- 010000
  ADD COLUMN gross_weight_g   NUMERIC(10,3),   -- 010000
  ADD COLUMN tare_weight_g    NUMERIC(10,3),   -- 010000
  ADD COLUMN container_type   TEXT,            -- 010000
  ADD COLUMN brand            TEXT,            -- 050000
  ADD COLUMN variant          TEXT,            -- 050000
  ADD COLUMN serving_weight_g NUMERIC(10,3),   -- 050000
  ADD COLUMN unit_type        TEXT,            -- 050000
  ADD COLUMN density_g_per_ml NUMERIC(10,4),   -- 050000
  ADD COLUMN certified        BOOLEAN;         -- 050000

-- Stock lots gain last-touched tracking (010000)
ALTER TABLE chefbyte.stock_lots
  ADD COLUMN last_update_source TEXT
    CHECK (last_update_source IS NULL
           OR last_update_source IN ('manual','live_shelf','live_scale','catch_all')),
  ADD COLUMN last_update_ts    TIMESTAMPTZ;

-- plpgsql function: atomic event application (010000 → 040000 → 050000)
CREATE FUNCTION private.apply_shelf_event(
  p_user_id         UUID,
  p_device_id       UUID,
  p_scale_id        TEXT,
  p_kind            TEXT,
  p_event_kind      TEXT,
  p_product_id      UUID,
  p_delta_g         NUMERIC,
  p_occurred_at     TIMESTAMPTZ,
  p_client_event_id TEXT            -- added in 050000; required
) RETURNS chefbyte.shelf_event_result;
-- First statement: INSERT INTO chefbyte.shelf_event_log (...) VALUES (...)
--                  ON CONFLICT (user_id, client_event_id) DO NOTHING RETURNING event_id;
-- If the INSERT produced no rows the function returns the cached result
-- instead of mutating stock. Otherwise it updates stock_lots, writes
-- food_logs, stamps last_update_source, and back-writes the outcome
-- (applied / resolved_lot_id / reason) onto the shelf_event_log row.

-- Public pass-through used by the edge function (030000 → refreshed in 050000)
CREATE FUNCTION chefbyte.apply_shelf_event_admin(...same 9 args...)
  RETURNS chefbyte.shelf_event_result;
-- Exists because PostgREST config.toml only exposes public / graphql_public /
-- hub / coachbyte / chefbyte — private.* is not reachable over RPC.
```

RLS on all new tables: `(select auth.uid()) = user_id TO authenticated`. `shelf_event_log` is SELECT-only for authenticated users (writes are service_role via the edge function).

## 6. Risks + mitigations

| Risk                                                                   | Severity   | Mitigation                                                                                                                                               |
| ---------------------------------------------------------------------- | ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Per-event network round-trip delays classification                     | **Low**    | User already accepted this. Typical round-trip <200 ms; classifier call is seconds anyway                                                                |
| Cloud outage leaves classifier unable to identify                      | **Medium** | Keep last-successful `/catalog` response in memory as fallback; classifier runs against stale data with a warning flag on the event                      |
| Outbox drains slow enough to fill the disk                             | **Low**    | Cap outbox at 10 k rows, drop oldest; at typical event rates this is weeks of offline capacity                                                           |
| Single-item scale sends event before the user pairs it                 | **Medium** | Pi returns 200 to the ESP but drops the event locally + surfaces "unpaired" on Pi's local UI + heartbeat bumps review count                              |
| Barcode intake stalls during ref-photo capture if Wi-Fi drops mid-flow | **Low**    | Product row is already created in cloud before ref-photo step; ref photos are local only, so Wi-Fi drop after cloud write is fine — Pi completes locally |
| ID swap (Pi's old local UUIDs vs cloud UUIDs)                          | **Low**    | Line-in-the-sand at migration day: wipe Pi's local `products`/`lots` on first boot with `CLOUD_ENABLED=1`, start fresh                                   |

## 6.1 Cloud event kinds

`shelf-ingest` POST /event accepts the following `event_kind` values
(see `supabase/functions/shelf-ingest/index.ts::VALID_EVENT_KINDS`).
Any new kind must be added BOTH to that constant AND to a branch in
`private.apply_shelf_event` — the Pi-side `TestEmitHandleMatrixSync`
meta-guard fails the build if the two drift.

| `event_kind`       | Mutates qty?              | Writes `food_logs`?                    | Clears in_flight marker?                                                 | Pi producer                                                                                         | Cloud handler migration |
| ------------------ | ------------------------- | -------------------------------------- | ------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------- | ----------------------- |
| `consumed`         | yes (decrement)           | yes (servings → macros)                | only when pickup_event_id matches a stuck-in-flight lot (20260427010000) | reconciler `consumed_or_removed` / `use_return_consumed` / single-item negative deltas / TTL reaper | 20260419010000          |
| `depleted`         | yes (zero)                | yes                                    | only via pickup-resolve detection                                        | single-item zero-floor reads                                                                        | 20260419010000          |
| `added`            | yes (increment / new lot) | no                                     | yes (clear-on-add via `resolve_add_to_shelf_lot`)                        | reconciler `new_arrival` + intake first-placement                                                   | 20260419010000          |
| `refilled`         | yes (increment)           | no                                     | yes (same as `added`)                                                    | reconciler `topped_up`                                                                              | 20260419010000          |
| `in_flight_pickup` | no                        | no                                     | sets `in_flight_since` + `pickup_event_id`                               | scale_events fast-path REMOVE branch                                                                | 20260425080000          |
| `in_flight_return` | no                        | no                                     | clears `in_flight_since` + `pickup_event_id`                             | scale_events fast-path return + TTL reaper companion emit                                           | 20260425080000          |
| `discarded`        | yes (zero)                | **no** (manual discard — not consumed) | yes                                                                      | Pi web UI `POST /api/lot/<lot_id>/delete` (× button on `/inventory`)                                | 20260427020000          |

The `discarded` kind exists specifically so the Pi `/inventory` remove
button can propagate to cloud WITHOUT polluting macros. Decision
rationale: see `decisions.md` #44.

## 7. What v1 explicitly does NOT do

- No photo/video upload
- No cloud UI for review triage — review stays Pi-local
- No bidirectional commands (cloud → Pi)
- No Realtime subscriptions from Pi — pull-per-event is enough
- No multi-Pi per user
- No auto-create products from unknown barcodes — assumes user has intaken products before placing on scales

## 8. Confidence: ~90%

Lower risk than prior versions because we dropped:

- Supabase Storage bucket RLS (the one genuinely new pattern)
- Sync loop + cache coherence complexity
- Unmatched events tray + cloud-side triage UI

Remaining unknowns are all engineering details with precedent, not architecture questions. Biggest wildcard is offline classifier degradation behavior — we'll see it in the E2E test.
